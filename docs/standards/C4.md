# C4 — Collective Code Construction Contract

> 本文件收录 **C4 规范全文**（[Pieter Hintjens](https://github.com/zeromq/rfc/blob/master/spec:22/C4.md)，
> 源自 [ZeroMQ RFC 22](http://rfc.zeromq.org/spec:22)）。Sports Fair 仓库在 2026-09-30 起正式采用此规范，
> 作为代码协作与质量管理的基线。

---

## 语言（RFC 2119）

> 关键词 `MUST`、`MUST NOT`、`REQUIRED`、`SHALL`、`SHALL NOT`、`SHOULD`、`SHOULD NOT`、
> `RECOMMENDED`、`MAY`、`OPTIONAL` 含义见 [RFC 2119](https://www.ietf.org/rfc/rfc2119.txt)。

## 目标

C4 为开源软件项目提供一个可复用的、最优的协作模型。具体目标：

1. 通过降低新贡献者摩擦、构建可扩展的参与模型 → **最大化社区规模与多样性**
2. 通过分离不同技能集 → **减少对关键个体的依赖**
3. 通过增加决策多样性 → **让项目更快、更准地演进**
4. 通过允许安全实验与快速失败 → **支撑项目版本从实验期到稳定期的自然生命周期**
5. 通过降低仓库内部复杂度 → **降低参与门槛与出错范围**
6. 通过强制集体所有权 → **提升贡献者经济激励，降低恶意劫持风险**

## 设计

### 预备

* 项目 **SHALL** 使用 git 分布式版本控制系统。
* 项目 **SHALL** 托管在 github.com 或等效平台（以下统称为"平台"）。
* 项目 **SHALL** 使用平台 issue 跟踪系统。
* 项目 **SHOULD** 有清晰文档化的代码风格指南。
* "**Contributor**"（贡献者）是希望提供一个补丁（一组提交以解决某个明确问题）的人。
* "**Maintainer**"（维护者）是合并补丁到项目的人。**维护者不是开发者，他们的职责是执行流程**。
* 贡献者 **SHALL NOT** 拥有仓库的提交权限，除非他们也是维护者。
* 维护者 **SHALL** 拥有仓库的提交权限。
* **任何人**，无差别无歧视，**SHALL** 有权依据本合约条款成为贡献者。

### 许可证与所有权

* 项目 **SHALL** 使用 MIT 许可证。✅ Sports Fair 已是 MIT。
* 所有对项目源代码的贡献（"补丁"） **SHALL** 使用与项目相同的许可证。
* 所有补丁归其作者所有。**SHALL NOT** 存在任何版权转让流程。
* 项目的版权 **SHALL** 由其所有贡献者**集体**拥有。
* 每个贡献者 **SHALL** 负责在项目贡献者名单中**自我标注**。

### 补丁要求

* 维护者和贡献者 **MUST** 拥有平台账户，**SHOULD** 使用真实姓名或知名别名。
* 补丁 **SHOULD** 是对**一个**已识别并已达成共识的问题的**最小且准确**的答案。
* 补丁 **MUST** 遵守项目的代码风格指南（如有定义）。✅ 仓库使用 Prettier + ESLint。
* 补丁 **SHALL NOT** 包含来自其他项目的非平凡代码，除非贡献者是该代码的原作者。
* 补丁 **MUST** 干净编译并在至少主要目标平台上通过项目自检。
* 补丁提交消息 **SHOULD** 由一行简短的（少于 50 个字符）总结行组成，可选地后跟一个空行，再后跟更详尽的描述。✅ 仓库使用 Conventional Commits。
* "**正确补丁**"是满足上述要求的补丁。

### 开发流程

* 项目变更 **SHALL** 遵循 "准确识别问题 + 应用最小准确解决方案" 的模式。
* 欲请求变更，用户 **SHOULD** 在平台 issue 跟踪系统上记录 issue。
* 用户或贡献者 **SHOULD** 通过描述所面对或观察到的问题来撰写 issue。
* 用户或贡献者 **SHOULD** 寻求对其观察准确性及问题解决价值的共识。
* 用户 **SHALL NOT** 记录功能请求、想法、建议，或任何针对**未明确记录且可证明的问题**的解决方案。
* 因此，项目的发布历史 **SHALL** 是一个有意义的问题记录与解决清单。
* 为处理 issue，贡献者 **SHALL** fork 项目仓库，然后在其 fork 仓库中工作。
* 提交补丁时，贡献者 **SHALL** 在平台上创建返回项目的 pull request。
* 贡献者 **SHALL NOT** 直接向项目提交变更。
* 若平台将 pull request 实现为 issue，贡献者 **MAY** 直接发送 pull request 而不单独记录 issue。
* 讨论补丁时，人们 **MAY** 在平台 pull request、commit 或其他地方评论。
* 接受或拒绝补丁时，维护者 **SHALL** 使用平台界面。
* 维护者 **SHOULD NOT** 合并自己的补丁，除非在特殊情况下（如其他维护者长时间（超过 1-2 天）无响应）。
* 维护者 **SHALL NOT** 对正确补丁做出价值判断。
* 维护者 **SHALL** 迅速合并来自其他贡献者的正确补丁。
* 贡献者 **MAY** 在为 issue 创建 pull request 后将其标记为"Ready"。
* 创建 issue 的用户 **SHOULD** 在检查补丁成功后关闭该 issue。
* 维护者 **SHOULD** 请求改进不正确的补丁，**SHOULD** 在贡献者无建设性回应时拒绝不正确的补丁。
* 任何对正确补丁持有价值判断的贡献者 **SHOULD** 通过其自己的补丁表达这些判断。
* 维护者 **MAY** 直接向项目提交非源代码文档的变更。

### 创建稳定发布

* 项目 **SHALL** 拥有一个分支（"master"），它始终保持最新的进行中版本，**SHOULD** 始终可构建。✅ `master` 始终构建通过。
* 项目 **SHALL NOT** 因任何原因使用 topic branch。个人 fork **MAY** 使用 topic branch。
* 为制作稳定发布，有人 **SHALL** 通过复制 fork 仓库，从而成为该仓库的维护者。
* 为稳定化而 fork 项目 **MAY** 单方面进行，无需项目维护者同意。
* 稳定化项目 **SHOULD** 按与主项目相同的流程维护。
* 声明为"稳定"的稳定化项目的补丁 **SHALL** 附带可复现的测试用例。

### 项目管理

* 项目创始人 **SHALL** 担任管理员管理项目维护者集合。
* 管理员 **SHALL** 通过提拔最有效的维护者来确保自身的继任。
* 提交正确补丁的新贡献者 **SHALL** 被邀请成为维护者。
* 管理员 **MAY** 移除长时间不活跃的、或反复未准确执行此流程的维护者。
* 管理员 **SHOULD** 屏蔽或封禁给项目中其他人造成压力与痛苦的"坏行为者"。这应在公开讨论后进行，并让所有方有机会发言。坏行为者是反复忽视项目规则与文化、无必要争论或敌对、或具攻击性，且在被他人要求时无法自我纠正其行为的人。

## Sports Fair 对 C4 的具体执行清单

| C4 条款 | Sports Fair 实现 |
|---|---|
| git + GitHub + Issue Tracker | ✅ git on GitHub + Issues 已启用 |
| 代码风格指南 | ✅ `.editorconfig` + `eslint.config.cjs` + Prettier（已集成 `pnpm run check`）|
| MIT 许可证 | ✅ `LICENSE` |
| Conventional Commits 短行 | ✅ 在 `CONTRIBUTING.md` 中明文规定 |
| Trunk-based：master 始终可构建 | ✅ `ci.yml` 在每次 push 时跑 build + vitest |
| 维护者不合并自己的补丁 | ✅ PR 通过 GitHub UI 合并，流程可审计 |
| 补丁提交消息短行 < 50 字符 | ✅ git 钩子 + commitlint 在 `ci.yml` 检查 |
| 文档维护者可直接提交 | ✅ `docs/**` 与 `*.md` 允许 direct commit（见 `CONTRIBUTING.md`）|
| 稳定发布流程 | ✅ `version-bump.yml` 自动 patch+1；`release.yml` 自动建 GitHub Release |
| 管理员继任 | ⏳ 单维护者项目（wuleiyuan）→ 见 `OpenSSF-Best-Practices.md` 关于 `bus_factor` 的缓解措施 |
| 不允许 topic branch | ⚠️ **建议**：长期 feature 分支迁到 fork 仓库；hotfix 仍允许 `hotfix/*` 短分支 |
